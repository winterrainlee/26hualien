# publish-note

화롄 경험 지도에서 **지역에 연결되는 노트**를 발행하는 스킬이다.

이 스킬의 목적은 기록을 빠르게 쌓는 것이다. 장소 데이터 정리, 좌표 조사, 사실 보강을 하지 않는다.

## 저장 원칙

노트 원본은 `notes/*.md`에 **1노트 1파일**로 저장한다.

- 파일명(확장자 제외)은 안정적인 노트 ID다.
- 제목이 바뀌어도 기존 파일명은 함부로 바꾸지 않는다.
- `notes.js`는 생성 파일이다. 직접 편집하지 않는다.
- 브라우저용 데이터는 `python3 scripts/build_notes.py`로 다시 만든다.

향후 노트 간 링크가 생길 때도 파일명 기반 ID를 링크 대상으로 사용할 수 있게 기존 ID 안정성을 우선한다.

## 입력

필수 정보는 두 가지뿐이다.

- `title`: 노트 제목
- `region`: 노트를 연결할 지역

본문은 선택 사항이다.

- `body`: 노트 내용. 한두 줄 메모부터 긴 글까지 허용한다.

입력은 직접 전달된 텍스트일 수도 있고 로컬 초안 파일일 수도 있다.

로컬 초안은 사용자가 지정한 파일 또는 `.drafts/` 아래의 파일을 읽는다. 초안 파일은 원본으로 취급하고 수정하거나 삭제하지 않는다.

## 현재 지역

발행 전에 `map-data.js`의 `MAP_DATA.regions`를 읽어 현재 유효한 지역을 확인한다.

현재 기본 지역은 다음과 같다.

| regionId | 표시명 | 번체 |
| --- | --- | --- |
| `school` | 학교 | 志學村 |
| `city` | 시가지 | 花蓮市 |
| `shoufeng` | 소우펑 | 壽豐鄉 |
| `ruisui` | 루이수이 | 瑞穗鄉 |

표시명, 번체명, regionId 중 하나로 입력되어도 기존 지역과 명확히 대응되면 같은 지역으로 처리한다.

하나의 노트를 여러 지역에 연결할 수 있다. 이때 front matter의 `regions`에 regionId를 쉼표로 나열한다.

새 지역을 임의로 만들지 않는다. 기존 지역에 대응되지 않으면 사용자에게 물어본다.

## Markdown 파일 형식

최소 형태:

```md
---
title: 노트 제목
regions: ruisui
---
```

본문이 있는 형태:

```md
---
title: 노트 제목
regions: ruisui
---

첫 문단.

두 번째 문단.
```

여러 지역:

```md
---
title: 지학역과 소우펑의 관계
regions: school, shoufeng
---

본문...
```

## 파일명 / ID 규칙

새 노트 파일명은 기존 파일과 충돌하지 않는 짧은 kebab-case를 우선한다.

예:

```text
notes/ruisui-guava-tea.md
notes/zhixue-daily-life.md
```

자연스러운 영문 슬러그를 만들기 어렵다면 다음 형식을 사용한다.

```text
notes/note-<regionId>-<YYYYMMDD>-NN.md
```

날짜는 내용의 사건일을 추측하지 말고, 별도 날짜 정보가 없으면 발행일을 사용한다.

기존 노트 파일명을 변경하면 향후 링크가 끊어질 수 있으므로, 사용자가 명시적으로 ID 변경을 요청하지 않는 한 rename하지 않는다.

## 본문 규칙

- 사용자가 본문을 주지 않았다면 front matter만 있는 파일도 허용한다.
- 본문이 있으면 원문의 의미와 말투를 유지한다.
- 맞춤법 교정이나 윤문을 요청하지 않았다면 과도하게 다시 쓰지 않는다.
- 문단 사이 빈 줄을 유지한다.
- 긴 본문을 짧게 요약해서 대체하지 않는다.
- 사용자가 적지 않은 사실을 보충하지 않는다.
- Markdown 표기나 링크가 이미 들어 있으면 원문 구조를 불필요하게 제거하지 않는다.

## 처리 규칙

1. `notes/`, `notes.js`, `map-data.js`를 확인한다.
2. 제목과 지역이 명확한지 확인한다.
3. 기존 파일명, 제목, 지역을 비교해 중복 여부를 확인한다.
4. 새 노트라면 `notes/<id>.md`를 만든다.
5. 본문이 있으면 원문의 문단 구조를 유지해 저장한다.
6. `python3 scripts/build_notes.py`를 실행해 `notes.js`를 재생성한다.
7. 다른 파일의 장소 데이터는 수정하지 않는다.
8. 검증 후 커밋하고 푸시한다.

## 절대로 하지 않는 것

- `notes.js`를 원본처럼 직접 편집하지 않는다.
- 본문에 나온 장소를 자동으로 스팟으로 만들지 않는다.
- 주소, 좌표, 장소의 공식 명칭을 조사하지 않는다.
- 장소 존재 여부를 확인하기 위해 웹 검색하지 않는다.
- 노트를 특정 장소에 강제로 귀속시키지 않는다.
- 사용자가 말하지 않은 사실이나 경험을 만들어내지 않는다.
- 제목이나 본문을 과도하게 문학적으로 고치지 않는다.
- 새 지역을 자동 생성하지 않는다.
- `data/places.json` 또는 지도 생성 데이터를 수정하지 않는다.
- 기존 노트 ID를 이유 없이 바꾸지 않는다.

## 애매할 때

다음 경우에만 사용자에게 질문한다.

- 제목이 없고 초안에서도 제목을 안정적으로 만들 수 없는 경우
- 지역이 없거나 둘 이상으로 해석되는데 복수 지역 연결 의도도 불명확한 경우
- 같은 제목 또는 매우 유사한 노트가 이미 있어 새 노트인지 수정인지 판단할 수 없는 경우

본문의 다른 표현이나 세부 사실이 애매해도, 사용자가 쓴 기록을 그대로 보존할 수 있다면 묻지 않는다.

여러 초안을 한 번에 처리할 때 일부만 애매하면 명확한 항목은 준비해 두고, 애매한 항목만 질문한다. 사용자가 부분 발행을 지시하지 않았다면 질문이 해결되기 전에는 해당 배치 전체를 커밋·푸시하지 않는다.

## 검증

수정 후 최소한 다음을 확인한다.

```sh
python3 scripts/build_notes.py
node --check notes.js
node --check app.js
```

가능하면 실제 페이지에서 다음도 확인한다.

- 해당 지역의 우하단 노트 개수가 맞다.
- 노트 목록에 새 제목이 보인다.
- 제목을 누르면 상세 읽기모드가 열린다.
- 긴 본문은 팝업 내부에서 스크롤된다.
- `← 목록`으로 같은 지역의 노트 목록에 돌아온다.

## 커밋

사용자가 발행을 요청한 경우 검증 성공 후 현재 작업 브랜치에 Markdown 원본과 재생성된 `notes.js`를 함께 커밋하고 푸시한다.

예:

```text
Add Ruisui region note
```

## 완료 보고

완료 후 다음만 간단히 알려준다.

- 추가한 노트 제목
- 생성한 Markdown 파일
- 연결한 지역
- 본문 포함 여부
- 검증 결과
- 커밋/푸시 결과

노트 발행 과정에서 장소 구조나 지도 설계를 다시 설명하지 않는다.
